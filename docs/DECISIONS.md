# Decisions

One row per decision that would otherwise be re-argued: what holds, why, and
what else was considered. Every row describes the present. To change one,
replace it in the same change that changes the code, and say in the commit
what it replaced; this file does not keep the old row.

The complement is [RESERVATIONS.md](./RESERVATIONS.md): what is *not* settled.

## Product

| Decision | Why | Instead of |
| --- | --- | --- |
| The WorkLedger is the source of truth; the trackers are the only human surface | Durable state must survive a crash; isolated directories are a consequence of the ledger, never the source. The operator must not open the ledger to know where a Ticket stands: the emitter's events are the whole human surface | Isolated directories or a tracker as truth; a ledger UI; humans driving each Gate |
| Two layers: a Feature (functional, in a FeatureTracker) holds Tickets (technical, in a TicketTracker); an Authority holds the lines | A need and the work that builds it are not the same thing and may live in different tools (a product tool for the first, the code tracker for the second). One issue playing both roles made the unit of work unnamed and the word *feature* misleading. Each layer is a Port a manager package answers; `manager-github` answers all three on one repository today | One tracker for both with Subtasks inside; naming the unit of work *Feature*; a single `ManagerPort` |
| A Ticket is one unit of work: the system does not split it | The split is made upstream, in the Tickets, and a human validates that list. A second split by the system was a non-validated layer that cost an agent run per Ticket and returned one unit on a Ticket already sized for one. Attempts and repair stay per Ticket | A Planner (FeatureBreakdown) turning a Ticket into Subtasks; Subtasks as internal commits |
| One open Feature per Project and at most `ticket.maxParallel` active Tickets in it (default 1; above 1 needs an Authority, so Tickets land one by one); a Feature is whole before another opens | Isolation and integration stay simple, and a Feature's line is one branch at a time. Among Features that may open, priority then age; among a Feature's Tickets, blockers then priority then age. Replaces "one active Ticket", which the code no longer enforces | Interleaving Tickets of several Features by priority |
| A Feature opens when it is `feature-ready`, its blockers are `done`, and all its Tickets are `task-ready`; `task-ready` is set on all Tickets together after the list is validated | Tickets are published one at a time, blockers first. A rule on one Ticket would start the first before the rest, or fold a Feature whose last Tickets did not exist yet. One signal on the Feature and one on each Ticket, each with its own meaning (content final / specification final) | A label per Ticket alone; a go signal added on a timer |
| A Feature has a line; its Tickets land on it and the line is submitted whole. `merge-when-ready` lets the system fold it, else a human merges and the system waits | The final line receives one reviewed unit per Feature. Tickets are checked by Gates and merged automatically, so the Feature's merge is the one place a human reads the whole; making it the default keeps the human in. The system starts no other Feature meanwhile, because a later Feature would be cut from a line without this one | Landing each Ticket on the final line; always automatic; always human; working on independent Features while one waits |
| Nothing enters a Feature's line until the Ticket passed its Gates **and** the assembled Ticket was judged | The two sequences are separate: a check right while the work is made can be wrong once it is assembled | Folding the Builder's output straight into the line; one Gate sequence for both |
| The human is an escape hatch, not the engine | The happy path completes with no approval except the Feature's merge when it is not automatic; an escalation freezes the Ticket and carries a Trace | Human validation of every Ticket; silent retries with no Trace |
| Work reaches a line through a Submission judged by an outside Authority; WorkLineStable is the system's copy of the line that Authority holds | A local fold makes the work invisible: no branch, nothing an outside check can run against. The Authority runs the checks the team trusts; its refusal carries a report and feeds the next Attempt like a Gate's, so there is one failure path. Once it folds, the copy is stale and the next Isolation starts from the new state. With no Authority, WorkLineStable is the reference and the fold is local | A second error path for outside refusals; a human approving each Submission; treating the copy as the reference and letting the Authority diverge |
| Just before a fold, the Authority is asked whether the line moved on since the Ticket was aligned (`AuthorityPort.behind`); if it did, the Ticket goes back to `integrating` (`recordRealign`), is aligned and judged again, and is offered again on the same Submission | The Gates judge the Ticket as published. A fold onto a line that moved would put on it something nobody judged, and a merge that GitHub accepts without a textual conflict says nothing about that. Today only a person can move the line while a Ticket waits (tickets run one at a time), and the same check is what lets that shortcut go. A realign is not a refusal, so it asks no repair of `assembly.fix` and spends no refusal; it has a ceiling of its own, `maxRefusals`, so a line that keeps moving escalates instead of looping. An Authority that cannot say answers `unavailable` and the fold waits: never `current`. A manager without `behind` is folded unchecked, as before | Re-checking inside the Gates (they run before the wait, so they cannot know); rebasing the Ticket onto the new line (the Integrator never rewrites history); folding and relying on GitHub's own conflict check alone |
| Everything that goes wrong after the work was made is corrected, not stopped on: an align conflict, a failed recheck, a refusal of the review or of the Authority, a line that moved. Each goes to `assembly.fix` with its reason and the Ticket restarts from the alignment; all draw on the one `maxRefusals` budget (`refusals + parked + realigns`) | A stop for a person is the most expensive answer and the one that teaches nothing: the loops exist so that a conflict or a red check does not wait for a human. A budget per loop lets a ticket bounce for as long as each loop is not empty; one budget bounds the ticket itself. A cause that no fix can touch (a blocking refusal, no fix declared) still stops | One budget per loop; stopping on a conflict; a separate ceiling for realigns |
| The system stops at the Project's final line | Release, deploy, and anything after the Feature's fold are somebody else's | A `publish` key that opens pull requests; Host flags named after one tracker |
| The names: Implementer runs one Ticket, Conductor sequences a Ticket and closes a Feature, WorkLedger stores | *Orchestrator* claimed coordination the Ticket runner does not do; *FeatureConductor* carried a tracker noun onto a sequencer that could deliver a book; *TaskBoard* read as a visual kanban | Orchestrator, Runner, Executor; FeatureConductor, Glue; TaskBoard, FeatureLedger |
| The operator live view (`mason watch` / `status`) is read-only | The team acts only in the trackers. The operator needs to see the machine without restarting the worker or opening the ledger by hand; watch snapshots the ledger and follows a journal, and cannot claim, cancel, or `resume` | Watch merged into `run` as a TUI (closing the screen would stop the loop); densifying `progress` on the tracker; parsing the persistence files |
| On a GitHub poll, a `resume` label on an `escalated` Ticket is `resume` | A listing is a snapshot with no `labeled` edge; without this a human who adds the label after an escalation is ignored | Requiring webhooks for resume; storing previous labels in the Cursor |
| A TicketStandard carries an intention and no list of acceptance criteria and no definition of done (the scenarios of a Feature are another thing: next row) | What the work must meet is said once, in the intention, and a Gate checks the result. A criteria list said again what the intention already said, and nothing checked one against the other | A required list nothing verifies; a definition of done written by a second agent |
| A Feature's scenarios are written, with ids S1, S2…, in the body of one last Ticket, the feature-test Ticket (the tracker's `feature-test` label), and a Gate proves them once on the assembled Feature | The row above holds because nothing checked a list of criteria against the work. Here something does: the scenarios become tests, and only those are run against the whole Feature before it is offered, so a Feature that passes every Ticket's Gates and every unit test but does not work is refused. They are decided with the operator before development and copied verbatim, and the Ticket that holds them is blocked by every other Ticket so that it lands last. The tests are not written first, per Ticket: that was tried, looped and cost too much on every Ticket | Acceptance criteria on every Ticket; tests written first per Ticket (tried: they looped and weighed on each Ticket); a suite per Ticket (run before the Feature exists, it can only fail); the scenarios in the Feature's own body (no Ticket to make the tests, no manifest to compare); the check left to a Project's CI alone |
| The feature-test check runs once per Feature, on the assembled line, in `feature.validate.gates`, and red feature tests refuse the line | The Feature's Gates run in Host's own copy of the line, where the whole product exists and nothing is shared with a Ticket. Red goes to `feature.fix` like any refusal of the line, with the tests frozen: the application is repaired, never the test. Blocking from the first day: a check that may be ignored is read as noise. The Project's whole suite is not run here (it grows with every Feature); the Project's CI is where it belongs | Running it per Ticket; running it only in CI after the fold; letting the fix edit the tests; running the whole suite for every Feature |
| Leaving the feature-test check out is declarative: a label on the Feature (`skip-feature-test`) and a `skipWhen: skip-feature-test` on the Gate; Host does not run that Gate for such a Feature and says so in the journal and the trace; no environment variable carries it | The convention is argv flags Implementer appends, and a Gate knows nothing of a Feature's labels. Reading the label in Host keeps the Gate a program with options and an exit, makes a skip visible in the film instead of a silent pass, and cancels the feature-test Ticket of a Feature that skips the check. A label put on or taken off is honoured until the Feature is submitted | An environment variable the Gate reads; a Gate option the operator edits per Feature; a Gate that passes when told to |
| The feature-test Ticket is made by its own pass `feature.test`, with its own command and Gates, nothing borrowed from `ticket.build.producer` or `ticket.build.repair`; it writes tests and the manifest `feature-tests/scenarios.json`, updates the existing tests a scenario changes, and its Gates are `tests-only` (nothing but tests and the manifest changes) and the Feature's own `feature-tests` Gate, which runs its tests against the built Feature after each attempt. A red run that is the author's (selector, wait, data) is repaired by the author; one that is the Feature's ends in `MASON_BLOCKED` with a diagnosis | The Feature is built when this Ticket runs. Tests written blind and never run were wrong on their first real use (`orangemonkey-site#106`: a locator by URL where the page shows the title, an `isVisible()` that does not wait), the Feature's fix cannot edit them, and so a person had to correct them one by one; the same run found a real defect (a transaction on a driver that has none) only at the Feature's Gate. An agent that could touch the application while writing its tests could make them pass by changing the application, so it may not, and may not lower a scenario either. The Gate runs again on the assembled line: it is the same program, and the second run catches what the integration changed | The shared producer with a longer prompt; tests written without ever being run; letting the author fix the application when its tests are red |
| A Project that declares the feature-test check refuses a Feature that holds neither a feature-test Ticket nor the skip label, as `invalid`, with a comment; one that does not declare it is unchanged | A Feature that silently lacks the suite is a Feature that was never proved, and the absence looks the same as a pass. A Project declares the check by `feature.test` and a Feature Gate with `skipWhen`, both or neither | Treating a missing feature-test Ticket as "nothing to run"; making the check mandatory for every Project |
| A Ticket's tests are written by its producer, with its code: there is no tests-first phase. `builder.tests`, the `no-tests` label (`noTestsLabel`), the `tests-red` and `tests-frozen` Gates, the `builders/tests.mjs` role and the ledger's `no_tests` and `first_stage_done` are removed with no compatibility (a config that still has `builder.tests` fails as any unknown key) | The phase was a required key whose one used value was `agent: false` (off in the only real Project since 2026-10-18): tests written before the code by another agent looped, were sometimes impossible to satisfy and cost on every Ticket. What it was for is done once per Feature, at its end, by the feature tests (the row above). Keeping it optional would keep a stage, a checkpoint commit, a label and two Gates nobody runs | Keeping it as an optional, default-off pass; tests-first only for the Tickets a label asks for |
| `mason.config.yaml` is grouped by level, `ticket` then `feature`, each in the order it is used: `tracker`, what makes the work (`ticket.build`, `feature.test`), `validate`, `gates`, `fix`. The old top-level `featureTracker`, `ticketTracker` and `builder` are gone, with no compatibility (a file that still has them fails as any unknown key) | The config had a tracker at the top, the Ticket's builder in `builder`, the Feature's test inside `builder` too, and the judging of each level in `ticket` and `feature`: one level's keys were spread over three blocks, in no order. The same five sections in the same order at both levels make a file readable top to bottom and comparable between levels. Host's internal model keeps its names (`featureTracker`, `ticketTracker`, `builder`, `builder.featureTest`); only the file and the names it prints changed | Keeping the flat keys and only ordering them; moving only the trackers |
| Feature orchestration (opening, ordering, closing, waiting on a human merge) lives in Host, not in Conductor | Conductor drives one Ticket; opening a Feature reads two trackers and the Authority, which only Host holds. Conductor stays a Ticket runner | A FeatureConductor in the kernel that would import the Ports of both trackers |
| Without an Authority there is no line: Tickets fold into WorkLineStable directly and a Feature is done when its Tickets are | A local directory has no branch to cut and no pull request to judge. The same loop runs, with nothing to wait for | Refusing to run a Feature without an Authority (reserved: C30) |
| A Ticket already in flight is not admitted again on a new delivery | A tracker's fingerprint moves with every comment the system writes; admitting on it would restart work on its own echo | Comparing only the intention text |
| The config names a package for the FeatureTracker and a package for the TicketTracker, each with its own options | The split between where a need is written and where the work is done is the core idea: Features in a product tool, Tickets in a code host. One package may serve both, and is then built once | One `manager` key answering both sides |

## Kernel

| Decision                                                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Instead of                                                                                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A kernel package imports nothing outside itself; Conductor may import WorkLedger                                                                                                                               | The same packages could deliver a book: they speak intention, attempt, directory — not GitHub, git, or a file format. `scripts/check-kernel.mjs` refuses the rest                                                                                                                                                                                                                                                                                         | A shared runtime library; a package under `plugins/` imported by a Transformer                                                                                                    |
| A Transformer is one IN, one job, one OUT                                                                                                                                                                      | A toolbox of operations is not a Transformer; the caller copies one OUT into the next IN                                                                                                                                                                                                                                                                                                                                                                        | One WorkSpace toolbox with many verbs; Conductor as a Transformer                                                                                                                 |
| Isolation is two Transformers: Isolator (Parent → Child) and Integrator (Child + Parent → `integrated` \| `conflict`, never forced)                                                                            | Implementer needs a directory it did not create; something must fold it back without forcing a merge                                                                                                                                                                                                                                                                                                                                                            | One WorkSpace toolbox; git commands in the caller                                                                                                                                 |
| A Transformer is a function; its CLI is a thin adapter                                                                                                                                                         | The composition root is TypeScript and must import or spawn a Transformer from one build                                                                                                                                                                                                                                                                                                                                                                        | CLI only; a library with no binary; two entry implementations                                                                                                                     |
| Builder and Gate are command slots, not Transformers                                                                                                                                                           | Implementer treats them as opaque children; the kernel runs without a chosen producer                                                                                                                                                                                                                                                                                                                                                                           | A Builder Transformer and a Gate Transformer                                                                                                                                      |
| Conductor talks to Transformers through an injected Transformer Port (`TransformerPort`); the name says what is behind it, like Manager Port, Persist Port and Authority Port                                  | The loop must be testable without a `dist/` and must not freeze the isolation method; the caller wires the four. Renamed from Brick Port on 2026-09-16: "Brick" was a word from the Block era with no glossary row and no meaning of its own                                                                                                                                                                                                                    | Conductor depending on the four packages; spawning CLIs from argv inside the loop; keeping Brick as a term in its own right                                                       |
| Isolator and Integrator receive a strategy; they do not sniff `.git`                                                                                                                                           | How a Child is attached and folded is one Project decision, made once. The CLIs require `--strategy`                                                                                                                                                                                                                                                                                                                                                            | Sniffing inside the Transformers; two config keys that can disagree; Conductor choosing                                                                                           |
| A fold backend may name the working files a failed fold restores (`snapshotPaths`); without it the kernel restores the whole Parent | A workspace is mostly `node_modules/`: the kernel's hand copy of it cost ~29 s per Integration (two or three a run, a third of a small task), while git's own commands took under a second. Only the backend knows what its fold writes — git never writes a path it ignores — so the list is its promise, and `isolation-git` makes it from `git ls-files --cached --others --exclude-standard` (~0.04 s, 285 files of 44 385) with no list to maintain | A kernel exclude list (`node_modules`): couples the kernel to JavaScript and goes stale for every other ecosystem. A Project-configured list (`isolationOptions`): the same list, kept by hand. Dropping the snapshot for git (RESERVATIONS F23): a failed fold can leave the working tree half written after `read-tree -u --reset`, and nothing else puts it back |
| Every child of a Task carries its own ceiling; there is no Attempt clock and no Task clock                                                                                                                     | A budget derived from a deadline once left the Gates a millisecond to judge in: the run lost the judgement, not just the build. What bounds a Task is `maxAttempts × (producer + Σ gates)`, arithmetic anyone can check                                                                                                                                                                                                                                         | Both clocks with each child capped under them; a hard-coded ceiling for a Gate that names none                                                                                    |
| The WorkLedger owns the Persistence Port; a backend owns the bytes                                                                                                                                             | SQLite or Postgres must not edit transition code. `src/ledger/` imports no adapter and no `node:fs`; a test asserts it                                                                                                                                                                                                                                                                                                                                          | `if (sqlite)` in the ledger; backend sniffing from an environment variable                                                                                                        |
| `EscalationKind` names where the whole stopped — `unit`, `assembly`, `submitted`, `merging` — and a refusal's report and its refuser's name stay on the record until a producing pass consumes them | An escalation reported as the unit that did not fail sent the reader to the wrong place; a Submission re-offered without its last report, or a repair told "the producer did not finish" when `ci-green` refused, gave the next Attempt and the human nothing to act on. `markSubmitted` carries `last_report` and `last_refused_by`, `escalate` takes the report that caused it, `ImplementInput.reportFrom` names the refuser all the way to `--report-from` | One `unit` kind for everything; rebuilding the Submission record field by field on republish; a report handed on unattributed                                                  |
| A repair produces **before** the Integration that takes its work up                                                                                                                                            | Fold, then produce, then publish left the repair loose in the workspace until the *next* round's fold: the Submission carried the state from before the repair and was refused again for the same reason, word for word, and the whole refusal budget went on the delay. `align` is the one Integration that commits what a producer leaves in the ticket workspace, so the producer runs first                                                                | Fold before produce; a second fold between produce and publish                                                                                                                    |
| Implementer's `Invocation` carries `gates` and `repairGates` as two sequences; which one judges an Attempt follows which producer ran it, not the Attempt number; Host fills both from `ticket.build.gates`                                               | `builderArgv` and `repairArgv` are different jobs, with different ceilings and often different agents, so they do not share one Gate sequence. A `--repair-builder` Attempt with no `--repair-gate` of its own runs ungated — a deliberate, documented consequence, not silently inheriting the producer's Gates                                                                                    | A third shared list; branching inside each Gate script on `--stage` the way `workspace-changed.mjs` already did for "assembly" (keeps the choice out of the Project's own config) |
| A producer that cannot act on what it was given says so with a last line `MASON_BLOCKED: <what is missing>`; the slot answers `fail-blocking` with that reason and the Task stops as `escalated` | Exit 0 meant "done", so an agent handed a refusal with nothing to act on had to change something to have anything to show: the fix of a CI refusal that carried only a link ran three times, ten minutes each, and committed changes nobody asked for, whose deployment failed in turn. A way to say "not enough" belongs to the producer contract, not to any one refuser (CI, a Gate, a person), and the contract already had the shape: `fail-blocking` with a reason, like `assembly.validate`'s `MASON_VERDICT:` line | A skill telling the agent to stop: nothing read the stop. A special case in `ci-green` for failures that carry only a link, or a wait before judging: arbitrary, and tied to one refuser. More Attempts with a better prompt: the same blind pass again |
| Implementer tells each Gate the ceiling it is killed at (`--timeout-ms`); a Gate that waits on a CI answers `fail-blocking` itself shortly before it, naming what it waited for | A Gate killed by its clock stays `fail-retryable`, which is right for a Gate that runs the project's code (a hang can be the work's) but wrong for `ci-green` waiting on a CI that never answered: the work went to a fix agent with nothing to fix, three times, ten minutes each. Only the Gate knows whether its wait is about the work or about someone else, so it is the Gate that says so | Treating every Gate timeout as blocking: it would stop retrying a test suite the producer made hang. A special case in `ci-green` for one CI (Vercel): the next CI would hit it again. A fixed wait in the config next to `timeoutMs`: two numbers to keep equal |
| Each Attempt after the first receives `--history`: the refusal the Task came with, then every Attempt (how its producer ended, what it said, each Gate's answer), bounded, oldest left out first; a killed producer's output is not repeated | The report an Attempt gets is the latest word only, and after a producer killed at its clock that word is "killed" plus the tail of its output: the third fix attempt of the Vercel failure never saw the Vercel failure. Implementer owns the Attempts, so it owns their history; the slots only place it in the prompt (`{{history}}`, optional) | Making the slot or the prompt remember: they are spawned fresh every Attempt. Passing the raw output of earlier Attempts: tens of kilobytes of tool noise (a test run's progress animation was the whole of one), which the film of the run (`observability.streams`) already keeps |

## Host

| Decision                                                                                                                                                                                                                                                               | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Instead of                                                                                                                                                                                                                                                                          |

That is many operations, not a Transformer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | A Conductor CLI that imports Transformers; the process as a walkthrough script                                                                                                                                                                                                      |
| `runtime` is four layers, one import direction: `config → plugins → loop → operator`                                                                                                                                                                                   | Host is where everything meets, so it is the package most likely to tangle. `scripts/check-host.mjs` refuses a backwards import, a fifth directory, and a file above the layers other than `index.ts` and `cli.ts`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | One flat `src/`; splitting `operator/` into its own package first                                                                                                                                                                                                                   |

| The reference work line is named by the ticket tracker (it holds the Authority) and read by the isolation strategy; Host copies the words through unread                                                                                                                                               | With an Authority the reference lives where the Authority is; the local directory is Host's copy. `referenceManager` returns an opaque record, `strategy.reference.parse` reads it strictly and hands back the target, an offline `inspect`, and a `materialize`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | `{ remote, branch }` typed in the kit (a git contract in the kernel); Host cloning from a key it reads itself; checking the copy lazily at the first Isolation                                                                                                                      |

| The system acts under its own identity: the token's account on the tracker, `commitAuthor` on its commits, the token on git transport. Only the issue is a person's                                                                                                    | Commits signed by the operator's machine and pushes over the operator's SSH key made a person the author of work an agent did. Host hands that environment to the Publisher and the Refresher only, never to its own process: a Builder must not inherit a token                                                                                                                                                                                                                                                                                    | SSH by default (the machine's key, the machine's account); an invented `Integrator <integrator@…>` author; the token in `.git/config` or in a URL; `process.env` set at boot (every Builder would inherit the credential)                                                           |
| Host may read a YAML config; Transformers do not                                                                                                                                                                                                                       | `mason run` has a dozen paths and slots; a file next to the clone is the operator surface, flags override it. | `mason.config.yaml` (YAML, parsed with the maintained `yaml` package) replaces the earlier JSON config; Host's own validation (`KNOWN_KEYS` and the per-field checks in `load-config.ts`) is unchanged — only the parse step moved                                     | JSON has no comments, and a `ticket.build.producer.gates.gates[].argv` array reads as a wall of quoted brackets; the hand-written validator already sits between the file and the invocation, so trading `JSON.parse` for a maintained parser costs one import, not a rewrite — the same call already made for `@octokit/core` over a hand-written client.
